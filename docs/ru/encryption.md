# Шифрование при синхронизации

[← Документация](../../README.ru.md) · [English](../en/encryption.md) · **Русский**

Включите **Настройки → Синхронизация → Шифровать всё перед отправкой**, и Zenith зашифрует
и содержимое файлов, *и* их имена прежде, чем что-либо покинет устройство. Сервер — Dropbox,
OneDrive, S3 или WebDAV — хранит шифротекст под нечитаемыми именами и пароля не видит
никогда.

Шифрованной синхронизации нужна отдельная папка. Зашифрованные и обычные файлы не могут
лежать вместе, поэтому папка, в которой уже есть заметки, будет отвергнута, а не смешана.

**Потерять пароль — потерять заметки.** Копии на сервере нет, в этом весь смысл. Пароль
лежит в `data.json` открытым текстом, как и все прочие учётные данные здесь: Obsidian не
даёт плагинам доступа к связке ключей. Так что делайте ему резервную копию так же, как
всему остальному, чего нельзя восстановить заново.

## Формат

Задокументирован, чтобы хранилище никогда не оказалось заложником этого плагина: всё
описанное ниже переписывается коротким скриптом поверх любой стандартной криптобиблиотеки.

В корне удалённой папки лежит файл `.zenith-crypt.json`, незашифрованный. Секретов в нём
нет — только параметры KDF, соль и контрольное значение:

```json
{
  "version": 1,
  "iterations": 600000,
  "salt": "<16 случайных байт, base64>",
  "check": "<32 байта, base64>"
}
```

Ключи выводятся один раз на удалённое хранилище, а не на каждый файл:

```
root        = PBKDF2-HMAC-SHA256(пароль, salt, iterations)            → 32 байта
contentKey  = HKDF-SHA256(root, info = "zenith/sync/content/v1")      → 32 байта
nameKey     = HKDF-SHA256(root, info = "zenith/sync/name/v1")         → 32 байта
nameNonce   = HKDF-SHA256(root, info = "zenith/sync/name-nonce/v1")   → 32 байта
check       = HKDF-SHA256(root, info = "zenith/sync/check/v1")        → 32 байта
```

HKDF используется с пустой солью. `check` сверяется с тем, что записано в маркере, — так
опечатка в пароле ловится до того, как что-то будет загружено, а не неделями позже.

**Содержимое файлов** — AES-256-GCM со случайным nonce, где путь файла в хранилище идёт
дополнительными аутентифицируемыми данными: те же байты, положенные по другому пути, не
расшифруются.

```
байты 0..3    сигнатура, ASCII "ZNC1"
байт  4       версия формата, 1
байт  5       алгоритм, 1 = AES-256-GCM
байты 6..17   nonce, 12 байт
байты 18..    шифротекст, с 16-байтным тегом в конце
```

Накладные расходы фиксированы и равны 34 байтам — это сделано намеренно: плагин может
вычислить расшифрованный размер файла из зашифрованного, не скачивая его, а план
синхронизации сравнивает размеры, решая, один ли это файл в двух копиях.

**Пути** шифруются посегментно, поэтому дерево папок сохраняется, а имена остаются
короткими. Каждый сегмент — это AES-256-GCM поверх текста сегмента, где дополнительными
аутентифицируемыми данными идёт открытый путь родителя, а nonce *детерминированный*: первые
12 байт `HMAC-SHA256(nameNonce, полный открытый путь до этого сегмента)`. Именно
детерминированность заставляет два устройства сойтись на одном имени вместо того, чтобы
каждое загрузило свою копию. Nonce хранится перед шифротекстом, потому что при расшифровке
его не пересчитать, а всё вместе кодируется в
[base32 по RFC 4648](https://www.rfc-editor.org/rfc/rfc4648), в нижнем регистре и без
дополнения:

```
сегмент = base32( nonce[12] || AES-256-GCM(nameKey, nonce, сегмент, aad = путь родителя) )
```

Base32, а не base64, потому что Dropbox сравнивает пути без учёта регистра, и два имени,
различающиеся только регистром, молча столкнулись бы.

## Что сервер всё равно узнаёт

Ни содержимого, ни имён. Но он видит, сколько файлов, примерно какого размера каждый, когда
каждый был записан, и форму дерева папок. Спрятать это можно только набивкой и ложным
трафиком, а они стоят реальной полосы и сделали бы невозможным то самое сравнение размеров.
Здесь мы останавливаемся там же, где останавливаются Remotely Save и rclone, и по тем же
причинам.
